The bootloader you need on the ATtiny85

twiboot v3.2 (patched for this board)
Flash code/twiboot/twiboot_rocket.hex with an AVR ISP programmer on J1. Built from twiboot 3.2 + code/twiboot/rocket.patch. Lives at 0x1C00 and answers on I2C 0x29.
lfuse0xE28 MHz internal
hfuse0xD5EESAVE + BOD 2.7 V
efuse0xFEself-program on
avrdude -c stk500v1 -P /dev/ttyACM0 -b 19200 -p t85 \
  -U lfuse:w:0xE2:m -U hfuse:w:0xD5:m -U efuse:w:0xFE:m \
  -U flash:w:code/twiboot/twiboot_rocket.hex:i

The factory fuses read E2 / DF / FF. Without the hfuse and efuse changes, twiboot can't write flash. You only do this once per chip. After that, the badge installs rocket_fw over I2C (lib/tiny_flash.py), and you never need the programmer again.

Take the rocket off the badge before using the Uno/ISP. The Uno's ISP lines are 5 V, and they would reach the ESP32's 3.3 V pins. J1 has no VCC pin, so power the rocket from SAO pin 1 separately.

I2C addresses on the bus

0x50–0x53LP5810. One chip uses four addresses, because the low address bits are register bits 9:8.
0x2AATtiny running rocket_fw (normal operation). ID register reads 'R'.
0x29ATtiny in twiboot: about 1 s after power-up, or after writing 0xB0 → reg 0x7F.

An empty scan with SCL stuck low means something is holding the bus. See the gotchas below.

ATtiny85 flash memory (8 KB)

Updating rocket_fw from the badge

  1. Badge writes 0xB0 to reg 0x7F at 0x2A. rocket_fw jumps straight to 0x1C00 (no watchdog reset).
  2. twiboot appears at 0x29. The badge sends "wait" so it doesn't time out.
  3. The badge checks the version string TWIBOOT and the ATtiny85 signature 1E 93 0B.
  4. It writes the pages top-down with page 0 last. An OSError on each page is normal, because twiboot NACKs the final byte.
  5. It reads back and verifies every page, then starts the app and waits for 0x2A.
from lib.rocket_sao import Rocket
from lib import tiny_flash
r = Rocket(1)
tiny_flash.flash_file(r.i2c, "/data/rocket_fw.bin",
    progress=lambda f: print("%d%%" % (f * 100)))

If it fails, the chip stays in twiboot, so just run it again.

Why twiboot needed patching

ChangeWhy
LED_SUPPORT 0The stock status LED would drive PB4 and RESET on this board.
Release SDA/SCL before starting the appThe bus is shared with the badge and the LP5810, so twiboot must not hold it.
App jump uses APPVECT_ADDR / 2The ATtiny85 has no hardware boot section. Stock code jumped to a byte address, so the app never started.

Standalone mode: if no host talks within 5 s of power-up, the ATtiny briefly becomes the I2C controller, starts a breathing animation on the LP5810, then goes back to listening.

Hard-won gotchas

Rocket "dead"? Unplug other SAOs.All SAO ports share one I2C bus. Another ATtiny85 SAO that uses PB0/PB2 as GPIO held SCL/SDA low and hid the rocket.
Never use the Uno/ISP while the rocket is on the badge.Its 5 V ISP lines would reach the ESP32's pins.
Never drive SAO GPIO2 (GPIO42) from the badge.ATtiny PB1 drives it as an output.
No watchdog reset into twiboot.twiboot doesn't clear the watchdog on the ATtiny85, so the chip would reset forever. rocket_fw jumps to 0x1C00 directly.
Release the USI after TinyWireM.Otherwise the USI start detector holds SCL low after the badge's first START, freezing the bus until a power cycle. Symptom: empty scan, SCL low, SDA high.
Flaky I2C? Reseat first.A half-seated rocket caused writes to cut off partway and then a stuck SCL. It looked exactly like a firmware bug.
Don't import the badge's lib/sao.py.It's a SyntaxError on the shipped MicroPython. Any import error in /apps stops the whole badge from booting, so check the serial log after deploying.
Low light readings are normal.Dim indoor light gives only about 100–300 mV on SENSE, and readings take about 0.5 s to settle (C1).
